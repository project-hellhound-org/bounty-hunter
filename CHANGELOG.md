# Changelog

Full detail on everything that's landed, in case you want the "why," not just the "what." README.md keeps only a short summary of the newest entries — this file has the rest.

## Recent Upgrades

- **`map_surface` — typed, prioritized attack-surface correlation (roadmap #3, second slice).** With `response_diff` already providing the diffing backbone, this closes the rest of roadmap item 3. A new `hellhound/core/surface_map.py` turns raw spider/recon output into a plan a human would make before fuzzing: (1) **param type inference** — every discovered parameter classified by DATA TYPE (numeric_id, uuid, email, file_path, url, token, search, json, boolean) from its name and any observed value, with the observed value winning over the name, each mapped to the test family it actually warrants (numeric_id → IDOR enumeration, file_path → LFI/traversal, url → SSRF/open-redirect, json → mass-assignment, search → SQLi/XSS, …) so the fuzzer sends type-appropriate payloads instead of a generic wordlist; (2) **endpoint grouping by function** — auth / payments / admin / upload / user / api buckets from path keywords (an endpoint can land in several, e.g. `/api/admin/users`), so the high-value groups get worked first; (3) a **ranked fuzz plan** ordering those groups by priority. It complements `generate_hypotheses` (which guesses vuln class from param NAMES) by adding value-based TYPE inference and functional grouping. Local/read-only, scope-gate- and pivot-exempt like `recall_data`/`profile` — it says what to test and in what order, it doesn't send traffic or record findings. Tool count 74 → 75. 34 tests (type inference incl. value-overrides-name and short-token false-match guards, multi-group endpoints, the seeded build + executor), all passing.

Down/Up move, Tab fills, Enter accepts-or-submits, Esc dismisses. This restores the single most-missed classic-UI affordance.
  - **Live working indicator** (`hellhound/core/tui_status.py`): a braille spinner + rotating Claude Code-style phrases ("On the hunt…", "Cooking…", "Wrapping up…") + elapsed/esc hint, so you can see a turn is actually running; it pins to the active tool name on `tool_start`. Only visible during a turn.
  - **Markdown replies** render again (bold/headers/lists/code) instead of showing literal `**asterisks**` — streamed raw for liveness, swapped to a rendered Markdown widget on finalize.
  - **No more leaked JSON**: finalize renders the authoritative cleaned return value (not the raw streamed buffer), with a last-ditch guard that refuses to render a bare `{"tool": …}` orchestrator tool-call blob as prose.
  - **`exit`/`quit`** now quit the app (were being sent as a prompt).
  - **Banner**: dropped the redundant "HELLHOUND · Bounty Hunter" label, restored the old at-a-glance info pane (model/provider, @handle, target + scope, recent targets) with red+white colouring instead of flat white, and opaque full-bleed background so the terminal wallpaper no longer shows through.
  - **`/program rename <old> <new>`** (new `rename_program` in `tasks.py`): fix a typo'd program name — moves the program directory, updates its record, and re-points every attached target's `.program` field and per-domain symlink. Guards against renaming onto an existing name or a non-existent one.
  - Headless Pilot coverage expanded to 27 TUI assertions + 11 program-rename assertions, all green.
- **Claude Code-style interactive terminal — a Textual full-screen TUI (`hellhound/core/tui.py`).** The long-standing visibility gap was that the console showed "a tool is running" with no window into what a `curl` (or any tool) actually sent and received. The new UI fixes that structurally: a scrollable transcript, a pinned input docked at the bottom, and **every tool call rendered as a clickable, collapsible card** — collapsed it's a one-line `✓ curl(url=…)`, expanded it shows the real status/headers/response body (and for `response_diff`, the field-level delta). It is the SHELL only — it reuses the exact same `Agent.handle_message` loop and `commands.dispatch` as the classic REPL, including the auto-continue behavior and Esc-to-cancel; the agent brain is untouched. A `TextualEmit` marshals every `emit`/`on_token` callback from the agent's worker thread onto the UI thread via `App.call_from_thread`. It's the default console now; the classic prompt_toolkit REPL remains available via `HELLHOUND_CLASSIC_UI=1` and is used automatically as a fallback if the TUI fails to start, so the console can never end up bricked. Verified with Textual's headless `run_test()` Pilot harness (15 assertions: boot, input→message, tool_start/result→collapsible card carrying the real response, streamed tokens, collapse/expand, input re-enable) — no TTY required. New dependency: `textual`. The hound banner logo is now solid vibrant red (was a coral/salmon accent that read as orange) in both the TUI and the classic banner.
- **`response_diff` — baseline-vs-test response diffing (roadmap #3, first slice).** The mechanical backbone for access-control / IDOR / BOLA / mass-assignment testing, and a direct answer to the VaultFi dry-run where `verify_finding` couldn't tell "no auth gate at all" from "genuine cross-account bypass." It fires a BASELINE request and a TEST request against the same endpoint and reports the exact delta: status, body length, and — when both bodies are JSON — a recursive field-level diff by path (`role: "user" -> "admin"`, a key present on one side and absent on the other, a list-length change), falling back to a bounded `difflib` line diff for non-JSON. The classic IDOR shape is one shared `url` with different `cookies` per side (victim baseline vs attacker test); mass-assignment is a GET baseline vs a GET after an unauthorized PUT. It deliberately reports "IDENTICAL / no field differs" as a first-class result, since that's the correct refutation of a large share of false IDOR claims. Both sides run through `_execute_curl` (so each inherits auto-attach/isolation/evidence-capture), both must resolve to the same host, and every resolved URL is re-checked against the scope rules inside the executor (defense in depth — the dispatcher's generic gate only inspects the top-level `url`, so a per-side override can't slip a second unvalidated host past it). It does NOT record or assert a finding — it feeds `verify_finding`/`record_finding`, whose EVIDENCE GUARDRAIL + VERIFICATION GATE are untouched. Tool count 73 → 74. 20 focused tests (pure field-diff helper + the real executor end-to-end against a local fixture HTTP server: identical/JSON-change/text-diff/error/same-host-refusal paths), all passing.
- **Persistent full target profile (roadmap #5 — "full target profiles beyond lessons-learned").** A single structured record of what we know about how a *specific host* behaves — as distinct from findings (what's wrong with it) or hypotheses (what might be). It lives at `target.state["profile"]`, so it persists in `task.json` and survives across sessions for free, and `format_profile_block()` injects it into both the orchestrator and synthesizer prompts every turn. What it holds:
  - **Tech stack** — folded in by reference from the existing `state["technologies"]` (not duplicated — one source of truth per fact).
  - **WAF/protection behavior** — detected WAF names (shared with `state["waf_detected"]`) plus a running count of requests that *looked* WAF-blocked (403/406/501 or a known block phrase), captured automatically from the curl path.
  - **Rate limiting** — every HTTP 429 observed on the curl path is recorded (count + last `Retry-After`), and the first one leaves a durable "this host enforces rate limiting — pace active testing" timeline note, so a resumed hunt paces itself instead of re-tripping the limit.
  - **Auth mechanism** — e.g. "session-cookie-only; Bearer header and `?api_key=` both return 401", recorded via the new tool once the model works it out.
  - **Quirks** — one-off behavioral oddities, deduped by text. The anonymous-session-cookie churn case (a fresh `PHPSESSID` minted on every anonymous page load — the exact VaultFi symptom that used to wedge the artifact gate) now auto-records itself as a profile quirk the first time it's detected, so the *reason* the gate stops re-blocking is visible in the profile rather than being invisible internal state.
  - New **`profile` tool** (`action='view'` / `action='note'`) — local-only, scope-gate- and pivot-exempt like `recall_data`/`recall_patterns`. Most of the profile fills in automatically; `note` is for durable observations the model reasons out itself. Tool count 72 → 73. 33 focused tests (dedup, persistence across a real save/reload cycle, the churn auto-quirk, the view/note executor), all passing.
- **Headless XSS execution confirmation** landed (roadmap item previously listed as open): `browser_control`'s `confirm_script_execution` action drives a real headless browser to confirm a payload *executes* (unique-marker check, safe dialog dismissal), and `verify_engine.verify_xss` now accepts that real-execution signal instead of treating unescaped reflection as proof on its own.
- **A full pass of real-world fixes from one actual VaultFi/localhost engagement log**, each traced to a specific symptom the researcher actually hit:
  - **Anonymous-session-cookie churn wedging the artifact pre-flight gate open forever.** Every unauthenticated page load on the test target minted a brand-new `PHPSESSID` (ordinary default PHP behavior, nothing to do with auth), and each new value was treated as a never-before-seen "high-value security artifact," so `spider`/`content_discovery` kept getting re-blocked by a fresh stale cookie moments after the previous one had already been tested dead. Fix: once a session-cookie field name has been seen once for a target, a later instance from a plain anonymous request is auto-marked consumed; a cookie minted by an actual login POST or SSO callback still gates normally (that's a genuinely new identity).
  - **`record_finding` attaching the wrong evidence to a confirmed SQLi.** A triager correctly flagged that the SQLi finding's "proof" was two identical 302 login responses with no sign of the actual SLEEP-based timing delay — because several unrelated, benign logins to the same URL happened *after* the sqlmap run (for unrelated SSO testing) and won the "most recent match to this URL" evidence lookup. For payload-driven classes (sqli/xss/ssti/ssrf/cmdi), evidence lookup now requires an actual payload marker in the match; falls through to `terminal_evidence_log` (where sqlmap's real output lives) when the curl log has none, and only falls back to the old generic match as a last resort if neither has anything.
  - **`browser_control` `fill`/`click` timing out on a guessed selector.** The researcher's own workaround in the log was `eval_js`-ing the DOM to find the real field by hand. Now automatic: on a timeout, it scans the page for a semantic match (name/id/placeholder token overlap, then input type, then submit-shaped buttons by type or text like "sign in"/"continue"/"approve") before giving up, and reports the fallback transparently (`fallback_note`, `original_selector`) rather than silently substituting.
  - **No internal signal when a tool is outright failing, only when it succeeds-but-finds-nothing.** The existing dead-end/pivot reflex (`_result_is_low_signal`) explicitly never counts a result carrying `error` — so `browser_control` timing out 6+ times across two sessions, while a curl-only version of the exact same SSO flow had already succeeded minutes earlier in the same conversation, produced zero signal telling the model to stop and use the proven path. Added a parallel error-streak tracker: 3 consecutive genuine tool errors escalates a note, 5 escalates to "STOP retrying — use whatever already worked instead." Never trips on a deliberate `blocked`/`requires_approval` stop (a scope gate is not flakiness, and must never read as encouragement to route around one).
  - **One combined report for unrelated vulnerabilities.** Real engagements submit one report per unrelated finding, not everything bundled together; `export_report` now defaults to splitting 2+ findings into separate standalone report files unless they're actually chain-related (reusing the same correlation logic as the finding-chain detector) or `combine=true` is passed explicitly.
  - **Indistinguishable saved-finding filenames.** Two findings on the same target both auto-saved as `finding_localhost_<timestamp>.html` — impossible to tell apart without opening each one. Both the auto-saved per-finding report and `export_report`'s per-finding split output now slug the finding's own title into the filename.
  - **No correct way to record "this was real and got fixed."** `dismiss_finding` only had one outcome — "this was never a real vulnerability" — which permanently blocks `record_finding` from ever flagging that exact (kind, endpoint) pair again. Using it for a retested-and-patched finding would have been factually wrong *and* would have silently hidden a future regression (the fix getting reverted, or the bug reappearing) forever. Added `resolution: 'patched'` as a distinct outcome: still removes the finding from the active list and report eligibility, but skips both the permanent re-flagging block and the false-positive lesson, writing a neutral "patched as of \<date\>" timeline note instead.
- **Real-time fuzzer output** — `ffuf` and `feroxbuster` now stream actual hit lines live as they're found (`[301] /admin`, `[200] /robots.txt`, ...), the same live-feed feel as the spider crawl, instead of a static "still running" placeholder for the whole scan.
- **Configurable rate limiting** — every fuzzing run (`content_discovery`, `vhost_fuzz`, `fuzz_hunter`) is capped at a sane requests/sec by default (`fuzz_rate_limit` in config, 150 by default) so an aggressive scan doesn't trip a WAF or lock out an account on a live target. Override per-call with `rate_limit`, or set it to `0` to go uncapped on a disposable lab/CTF box.
- **`/output`** — pull the complete stdout/stderr of the last tool run on demand. In-memory only, nothing extra written to disk.
- **`/program`** — group several in-scope domains of one engagement under a shared scope: create a program, set in/out-of-scope rules once, every attached domain inherits them. Entirely optional, never forced on a plain `/target` call, and switching between domains across different programs mid-session just works via `/target <domain>` — no restart needed.
- **Cleaner `/help`** — no longer dumps all 30 skill descriptions into the main command listing; that lives at `/skills` (or `/help skills`) instead.
- **`katana` + `jsluice`** added to the arsenal, for faster crawling and JS secret/endpoint extraction.
- **Correctness fixes** — no more duplicated "still running" spinner lines; a successful login with valid, given credentials is no longer auto-recorded as a finding; related hosts named up front (e.g. an OAuth/IdP server needed for legitimate auth testing) can be pre-authorized into scope in one shot instead of tripping the scope gate mid-flow.
- **`remember_lesson`** — a real "remember this" tool, called the instant a researcher asks the agent to retain something, instead of the agent just replying "noted" and forgetting it the moment the session ends. Writes to a durable cross-target lessons store and pins straight into the live session digest.
- **Real evidence for non-curl findings** — `sqlmap`/`hydra`/`nmap`/custom-script findings (anything run via `run_terminal_command`) now capture and attach actual command output as evidence, fixing reports that used to come back with just a tool banner and no real proof; long output is excerpted from both the start and the end so the actual payoff doesn't get cut off by progress noise in the middle.
- **`js_miner` now covers classic server-rendered apps** — it only recognized modern `fetch`/`axios`/absolute-path API calls before; it now also picks up relative, extension-based backend script references (`components/user/controller.php?action=...`-style), the dominant shape in PHP/ASP/JSP-era apps, which it previously found nothing on.
- **No more blind repeat recon calls** — `js_miner`/`js_static_analysis` now cache their result per target; an identical repeat call (same URL, same session) is served from cache with a "stop retrying this" note instead of silently re-running and wasting a turn on a call that's mechanically guaranteed to return the same thing.
- **Validation gate on `record_finding`** — for sqli/xss/ssrf/idor/access-control-category findings filed at critical/high severity, a captured request/response is no longer enough on its own; the agent has to assert `verified=true` with a real `verification_note` (a dumped row, a listener hit, a cross-account diff) or the call is blocked with class-specific guidance on what proof is actually needed. Low/medium "worth tracking as a lead" findings aren't gated.
- **Dead-end / pivot reflex (all tools, not just js_miner)** — any recon/exploitation tool that keeps coming back with nothing useful against a target, even across *different* args each call, now gets an escalating note stamped onto its own result after 3 consecutive low-signal calls, and a hard "stop, this avenue is dead — change approach" after 5. A genuinely useful result resets the streak.
- **Signal-chaining on `record_finding`** — a new finding is automatically cross-checked against every other finding already on the target for known high-impact combinations (open redirect + OAuth callback, SSRF + cloud metadata, XSS + weak session handling, subdomain takeover + anything on that host, exposed secret + auth endpoint, IDOR + mass assignment) and surfaced as `chain_candidates` — the agent stops reporting two separate low-severity blips when they actually combine into one account-takeover-grade chain.
- **`verify_finding`** — independent, code-level signal checking for sqli/xss/ssrf/ssti/cors/idor, sitting alongside (never replacing) the existing validation gate: replays the request live and runs a class-specific assertion (a real SQL error string, verbatim-unescaped reflection, a cloud metadata marker, an evaluated template expression, an exploitable CORS combination, another account's data appearing under your own session), optionally with a negative-control replay for a differential check that rules out generic-error-page/no-auth-at-all false positives.
- **`recall_patterns` + wired-up pattern memory** — every confirmed `record_finding` now also writes into a cross-target pattern store (keyed by vuln class + tech stack, payout/recency ranked) that `recall_patterns` can query — "this technique worked on a similarly-stacked target before" surfaces automatically instead of starting cold on every new target. The storage layer already existed in the codebase but was never actually called from anywhere; it's wired in now.
- **`capture_identity` + `swap_session`** — the two-account primitive IDOR/BOLA testing actually needs: snapshot a session under a name (`capture_identity`), then switch which one is "active" for curl/spider/every other network tool (`swap_session`) — no separate session-injection machinery, it just redirects the exact auto-attach logic curl already had. `swap_session(name="anonymous")` clears the session entirely for unauthenticated testing. This is what makes `verify_finding(kind="idor", ...)` possible: replay a victim's resource under the attacker's own (`swap_session`-activated) session, and check for a `victim_marker` string unique to the victim's data.
- **`generate_hypotheses` + `update_hypothesis`** — the tech-stack-driven reasoning step a human researcher (or a tool like XBOW/Horizon3) does before touching a single tool: once the stack is fingerprinted and a first pass of endpoints is known, `generate_hypotheses` runs a rule table (`hellhound/core/hypothesis_engine.py` — WordPress/Laravel/Django/Flask/Node+Mongo/Spring/ASP.NET/GraphQL/JWT signatures, numeric-ID path shapes, upload/webhook/SSRF-prone features, CORS headers already seen, exposed `.git`/`.env`, unauthenticated Elastic/Mongo/Redis, OAuth/SSO redirect handling, and discovered PARAMETER NAMES — a `redirect`/`return_url` param hints at open_redirect, `file`/`template` at LFI, `search`/`sort` at SQLi, `cmd`/`ping` at command injection — plus any WAF already fingerprinted, flagged as a reason to try `waf_evasion_probe` before writing a blocked payload-based hypothesis off as a dead end) against the target's real fingerprinted tech + discovered endpoints, and folds in any prior CONFIRMED technique from a similarly-stacked target via the pattern store. Returns a ranked, deduped LEAD BOARD with a plain-English rationale and a concrete test sketch per candidate vuln class — persisted on the target and shown every turn — instead of the agent defaulting to "enumerate the tool arsenal in order." `update_hypothesis` marks each lead tested/confirmed/refuted/deprioritized as the model works it. A hypothesis is a lead, never a finding — `verify_finding`/`record_finding`'s EVIDENCE GUARDRAIL and VERIFICATION GATE are completely untouched.
- **`wafbuster` now actually persists what it detects** — its WAF/protection fingerprint and tech-stack detections were computed every single call and then discarded; they now merge into `target.state["waf_detected"]`/`["technologies"]` (same pattern `httpx`'s tech detection already used), so a WAF `wafbuster` finds feeds `generate_hypotheses`' new WAF-aware lead automatically instead of needing to be re-detected or manually passed in.
- **`manage_program(action="create")` no longer requires `set_target` first** — it used to silently attach whatever target happened to be currently active, and every session starts on a bare, unset `"default"` placeholder target until `set_target` is actually called, so creating a program before ever setting a target polluted its target list with that placeholder as if it were a real in-scope domain. `create` is now a genuinely standalone action: it only attaches domains you explicitly list (`domains`), and only folds in the currently active target when it's a real, already-`set_target`'d one AND you ask for that with `include_current_target: true`. `set_target` is for actively hunting one specific domain, never a prerequisite for program bookkeeping. (The "each in-scope domain gets its own directory under the program" piece — `~/.hellhound/programs/<program>/targets/<domain>` as a live symlink to that domain's real target directory — already existed from an earlier fix and needed no change.)
- **`capture_identity`/`swap_session` ↔ `browser_control` bridge** — the two multi-identity primitives (curl/spider's named identity store, and `browser_control`'s own named Playwright contexts) used to be completely separate; logging in as "victim" in one was invisible to the other. Now: `capture_identity(from_browser_session=<name>)` pulls cookies straight out of a live browser session; `browser_control(session=<identity name>, action='goto')` auto-seeds that identity's cookies on its first navigation purely because the names match; and `swap_session` refreshes an already-open matching browser session's cookies too (checked via `list_sessions` first — it never spins up a new browser context as a side effect of a call that's supposed to stay a fast, local, no-network state write). Net effect: capture an identity once, drive it from curl, spider, or the browser interchangeably.
- **Identity model extended to `fuzz_hunter`, `sqlmap_scan`, and `hydra`** — these three used to run with whatever auth they were handed directly in the call, blind to the session `capture_identity`/`swap_session` had active. Now all three auto-attach the active identity: a captured `auth_token`/`forged_token` (JWT or other bearer credential, not just a cookie) is added as an `Authorization: Bearer` header wherever it's missing — the same thing curl already did, now shared through one helper instead of being curl-only — and `hydra` (parameter/logic-flaw analysis) and `fuzz_hunter`'s internal fallback engine (only runs when neither feroxbuster nor ffuf is installed) now carry the active cookies/headers into every request they fire, which they didn't do at all before. A multi-identity fuzz, sqlmap, or logic-flaw run no longer needs credentials passed by hand.
- **`generate_hypotheses` gets a richer signal source: hydra's real per-parameter role findings** — `hydra` (parameter/logic-flaw analysis) already computes a role per discovered parameter (ADMIN_FLAG, AUTH_PARAM, PATH_REFERENCE, GRAPHQL_INTROSPECTABLE, OAUTH_CALLBACK_SINK, with an impact score and the exact url+parameter it was seen on) but threw all of it away except the handful of findings that cleared the bar for an automatic `target.findings` entry — the same "computed and discarded" pattern `wafbuster` had before its own persistence fix. It's now persisted into `target.state["param_signals"]` (deduped by url+parameter, kept to the single highest-impact finding per pair, capped at 200 entries) and a new hypothesis_engine rule (`_rule_hydra_param_roles`) turns each role into a hypothesis anchored to the real endpoint it was seen on — materially stronger evidence than the pre-existing name-token-only rule (`_rule_param_name_signals`, which only ever sees bare discovered parameter NAMES like "redirect" or "cmd" with no idea if they're actually exploitable-shaped). Also added: `_rule_rails` (mass assignment via missing/misconfigured strong parameters, insecure YAML/Marshal deserialization) and `_rule_drupal` (the Drupalgeddon-class RCE history, node-access-matrix misconfiguration) — two more framework/CMS signatures alongside the existing WordPress/Laravel/Django/Flask/Node+Mongo/Spring/ASP.NET coverage.

- **`save_auth_flow` + `replay_auth_flow`** — the "record an auth flow once, replay it headless" half of the "persistent, scriptable browser" roadmap item. `browser_control` now records every state-mutating action (goto/click/fill/eval_js — not the read-only ones like get_cookies/screenshot) into a per-session ring buffer automatically, no separate "start recording" step to remember before driving a login. `save_auth_flow(name, session)` snapshots that buffer into a named, reusable flow; `replay_auth_flow(name, session, capture_identity_as)` replays the saved steps in order against a session that defaults to `<name>_replay` (never the live `default` session) so a replay can't silently clobber a session already in use. Stops at the first failed step rather than pushing through a broken flow, re-checks every recorded `goto` URL against the target's CURRENT scope rules before navigating (not just trusted because it was in scope when first recorded — scope can change between record and replay, and the Scope Security Gate is unconditional per AGENTS.md), and can automatically fold the resulting session into `capture_identity` on success so it's immediately usable via `swap_session`. Request/response interception — the other half of that roadmap item — is still open.

## Roadmap detail — superseded/landed items

The README's Roadmap section keeps only what's still genuinely open. The fuller reasoning behind a few items that were partly reworked as they landed:

- **Persistent, scriptable browser** originally bundled "multi-tab sessions for cross-user IDOR testing" together with record/replay and interception. The multi-tab/multi-identity piece is done — `browser_control`'s named-session primitive (`session="victim"`/`session="attacker"`, each an isolated Playwright context), now bridged to `capture_identity`/`swap_session` both ways. Record-once/replay-headless and request/response interception are what's left (see README).
- **Unified session state**: `capture_identity`/`swap_session` give curl/spider every other network-calling tool a named, swappable multi-identity session, bridged to `browser_control` (`capture_identity(from_browser_session=...)` pulls cookies from a live browser session; `browser_control(session=<identity name>)` auto-logs-in as that identity), and extended to `fuzz_hunter`/`sqlmap_scan`/`hydra` (bearer `auth_token`/`forged_token` auto-attach, not just cookies). Burp/Caido integration is the only piece left here.
- **Cross-session campaign memory** (landed): `remember_lesson` writes a durable, tech-signature-keyed lesson the moment a researcher asks the agent to remember something, pinned into the live session digest. Full target profiles beyond lessons-learned (WAF behavior, rate limits, auth mechanism, quirks) now also persist per target and surface into the prompt every turn via the `profile` tool / `format_profile_block()` — see the Recent Upgrades entry at the top. A lesson is cross-target ("this works on stack X everywhere"); a profile is about one specific host.
- **Validation over detection** (landed): `verify_finding` does real, code-level signal checking for sqli/xss/ssrf/ssti/cors/idor — a SQL error string, verbatim-unescaped reflection, a cloud metadata marker, an evaluated template expression, an exploitable CORS combination, another account's data appearing under the attacker's session — with an optional negative-control replay. idor/BOLA verification rides on the `capture_identity`/`swap_session` two-account primitive. Headless-browser XSS *execution* confirmation (vs. reflection-only) is now in too, via `browser_control`'s `confirm_script_execution` feeding `verify_xss`.
- **Report-ready evidence capture** (partially landed): non-HTTP-client tool findings (sqlmap, hydra, nmap, custom scripts) get real captured command output attached automatically, excerpted from both ends so the payoff survives. `record_finding` also cross-checks new findings against existing ones for known combination patterns, surfaced as `chain_candidates` (advisory only, never auto-escalates severity). Screenshots auto-attached per finding, and a wider chain-pattern set, are still open.
